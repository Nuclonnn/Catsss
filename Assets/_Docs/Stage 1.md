Мы будем собирать проект итеративно в пустой тестовой сцене Scene_Gym. Каждый этап должен заканчиваться рабочим, тестируемым билдом.
ЭТАП 1: Фундамент (Core Systems)
ОНБОРДИНГ. ЭТАП 1: Разработка Базовой Архитектуры (Core Systems)
Контекст для разработчика:
На этом этапе мы вообще не делаем игру. Мы не настраиваем прыжки кота и не спавним мышь. Твоя задача на ближайшие пару дней — написать и протестировать чистый, независимый C# код, который станет "кровеносной системой" нашего проекта.
Всё должно быть строго типизировано, модульно и готово к использованию в сетевой среде.

Задача 1.1: Кастомная Машина Состояний (FSM)
Мы используем объектно-ориентированную (не enum!) State Machine на основе интерфейсов. Она должна быть полностью отвязана от Unity API (без жесткой привязки к MonoBehaviour, чтобы её можно было покрыть юнит-тестами или крутить чисто на сервере).
Что нужно реализовать:
1.	Интерфейсы: Создай IState, ITransition, IPredicate.
o	IState должен содержать: OnEnter(), OnExit(), OnUpdate(), OnFixedUpdate().
2.	Классы связей: Реализуй Transition (хранит целевой IState и IPredicate) и FuncPredicate (оборачивает Func<bool> для условий перехода).
3.	Ядро StateMachine:
o	Должна хранить текущее состояние.
o	Должна иметь списки переходов: AnyTransitions (переходы из любого состояния, например, смерть/дисконнект) и обычные Transitions (привязанные к конкретным нодам).
o	Метод Update(), который сначала проверяет условия переходов (сначала Any, потом локальные), меняет состояние если нужно, и только потом вызывает _currentState.OnUpdate().

Задача 1.2: Шина Событий (SO-based Event Bus)
Наша игра общается через Scriptable Objects, чтобы избежать жестких зависимостей сцены (Decoupling).
Что нужно реализовать:
1.	Базовые классы: Абстрактный EventChannel<T> : ScriptableObject и EventListener<T> : MonoBehaviour.
2.	Безопасный Invoke (КРИТИЧНО!):
o	При реализации метода Invoke(T value) в EventChannel, ты обязан итерироваться по копии списка слушателей.
3.	Конкретные реализации: Создай пустышки типов, которые нам точно понадобятся:
o	EmptyEventChannel (для событий без данных, структура public readonly struct Empty{}).
o	IntEventChannel (например, для передачи ID игрока).
o	FloatEventChannel.

Задача 1.3: Микро-Сервис Локатор (Dependency Injection)
Мы не используем Singleton (типа Manager.Instance), так как они усложняют порядок инициализации и тестирование. Мы используем простейший Service Locator.
Что нужно реализовать:
1.	Создай статический класс ServiceLocator.
2.	Внутри: Dictionary<Type, object>.
3.	Методы: Register<T>(T service), Unregister<T>() и Get<T>().
4.	Безопасность: В методе Get<T>(), если сервис не найден, выбрасывай внятную ошибку: throw new Exception($"Service {typeof(T)} is not registered in ServiceLocator."); (чтобы мы не ловили молчаливые NullReference).

Задача 1.4: Архитектура Конфигов (Data-Driven Design)
Все глобальные настройки игры должны лежать в папке Configs/ в виде SO. Геймдизайнер не должен лазить по префабам на сцене, чтобы изменить высоту прыжка.
Что нужно реализовать:
1.	Создай класс SO_GameConfig : ScriptableObject.
2.	Внутри создай вложенные сериализуемые классы/структуры (для порядка в инспекторе):
o	PlayerMovementSettings (baseSpeed, jumpForce, dashCooldown).
o	PhysicsSettings (customGravityMultiplier).
3.	Сделай так, чтобы этот конфиг можно было создать через меню [CreateAssetMenu(menuName = "Configs/GameConfig")].
